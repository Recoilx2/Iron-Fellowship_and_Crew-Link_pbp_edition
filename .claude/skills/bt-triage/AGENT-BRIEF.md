# Writing Agent Briefs

An agent brief is the body of a new ticket, filed on `docs/agents/templates/bug.md` (category `bug`) or `docs/agents/templates/slice.md` (category `enhancement`) when a raw issue moves to `ready-for-agent`. It is the authoritative specification that an AFK agent will work from. The raw issue and its discussion are context, linked by `ticket.py new --from <n>`: the ticket body is the contract.

The brief states **what the agent should do**, which stretches to both surfaces: for an issue, that's building the change from nothing; for a PR, it's what's left to do *to the existing diff*: finish it, close gaps, address review points. Same principles either way; the PR example below shows the difference.

Follow the template exactly, with no `TBD`, `TODO` or `<...>` left in; `ticket.py lint` checks it.

## Principles

### Durability over precision

The ticket may sit in `ready-for-agent` for days or weeks. The codebase will change in the meantime. Write the brief so it stays useful even as files are renamed, moved, or refactored.

- **Do** describe interfaces, types, and behavioral contracts
- **Do** name specific types, function signatures, or config shapes that the agent should look for or modify
- **Don't** reference file paths: they go stale
- **Don't** reference line numbers
- **Don't** assume the current implementation structure will remain the same

### Behavioral, not procedural

Describe **what** the system should do, not **how** to implement it. The agent will explore the codebase fresh and make its own implementation decisions.

- **Good:** "The `SkillConfig` type should accept an optional `schedule` field of type `CronExpression`"
- **Bad:** "Open src/types/skill.ts and add a schedule field on line 42"
- **Good:** "When a user runs `/triage` with no arguments, they should see a summary of issues needing attention"
- **Bad:** "Add a switch statement in the main handler function"

### Complete acceptance criteria

The agent needs to know when it's done. Every agent brief must have concrete, testable acceptance criteria. Each criterion should be independently verifiable and name its proof: a command, probe or test.

- **Good:** "Running `gh issue list --label needs-triage` returns issues that have been through initial classification"
- **Bad:** "Triage should work correctly"

### Explicit scope boundaries

State what is out of scope in `## Out of scope`. This prevents the agent from gold-plating or making assumptions about adjacent features.

## Where each part goes

| Brief content | Bug template | Slice template |
|---|---|---|
| One-line summary | the ticket title | the ticket title |
| Current behaviour | `## Effect`, `## Expected vs actual` | `## What to build` (the status quo it builds on) |
| Desired behaviour, edge cases, error conditions | `## Expected vs actual` | `## Behaviour` (inputs → expected outputs) |
| Key interfaces (types, signatures, config shapes) | `## Expected vs actual` | `## Approach constraints` |
| How you reproduced or verified it | `## Reproduce`, `## Evidence`, `## Where found` (the raw issue) | `## Verify` |
| Acceptance criteria | `## Acceptance criteria` | `## Acceptance criteria` |
| Out of scope | `## Out of scope` | `## Out of scope` |

A bug's `## Root cause` reads exactly `Pending diagnosis.` until `bt-diagnosing-bugs` fills it in.

## Examples

### Good agent brief (bug)

Title: Skill description truncation drops mid-word, producing broken output

```markdown
Type: bug
Part of: none
Blocked by: none

## Effect
Skill descriptions over 1024 characters end mid-word (e.g. "Use when the
user wants to confi"), so the agent reads a broken trigger list.

## Reproduce
Load a skill whose SKILL.md frontmatter description is 1100 characters long,
then print the loaded `SkillMetadata.description`.

## Expected vs actual
Expected: truncation breaks at the last word boundary before 1024 characters
and appends "...".
Actual: truncation cuts at exactly 1024 characters regardless of word
boundaries.
Key interfaces: the `SkillMetadata` type's `description` field needs no type
change, but the logic that reads SKILL.md frontmatter and populates it must
respect word boundaries.

## Evidence
Reproduced during triage of #41; the printed description ends in "confi".

## Where found
Raw issue #41.

## Root cause
Pending diagnosis.

## Acceptance criteria
- [ ] Descriptions under 1024 chars are unchanged (unit test)
- [ ] Over 1024 chars, truncation breaks at the last word boundary (unit test)
- [ ] Truncated ones end with "..." and total ≤ 1024 chars with it (unit test)

## Out of scope
- Changing the 1024 char limit itself
- Multi-line description support

> *This was generated by AI during triage.*
```

### Good agent brief (enhancement)

Title: Track rejected feature requests in `.out-of-scope/`

```markdown
Type: slice
Part of: none
Blocked by: none

## What to build
Today a rejected feature request is closed as wontfix with a comment, and
nothing persistent records the decision or its reasoning, so the next similar
request means recalling or searching the old discussion. Rejected requests
should be recorded in `.out-of-scope/<concept>.md`, and triage should check
those files for matches.

## Behaviour
- An enhancement closed as wontfix → a file in `.out-of-scope/` with the
  decision, the reasoning and a link to the closed issue.
- A second request for the same concept → appended to that file's
  "Prior requests" list, no new file.
- A new issue matching a prior rejection → triage surfaces the file.

## Approach constraints
Each file has a `# Concept Name` heading, a `**Decision:**` line, a
`**Reason:**` line and a `**Prior requests:**` list with issue links. Triage
reads all `.out-of-scope/*.md` files early and matches by concept, not keyword.

## Verify
Run triage on a fixture enhancement issue twice; inspect `.out-of-scope/`.

## Acceptance criteria
- [ ] A wontfix close creates or updates a file in `.out-of-scope/` (fixture run)
- [ ] The file has the decision, reasoning and closed-issue link (fixture run)
- [ ] A match appends to "Prior requests", no duplicate file (fixture run)
- [ ] Triage surfaces an existing file when a new issue matches it (fixture run)

## Out of scope
- Automated matching (a human confirms the match)
- Reopening previously rejected features
- Bug reports (only enhancement rejections go to `.out-of-scope/`)

> *This was generated by AI during triage.*
```

### Good agent brief (PR)

For a PR, `## What to build` describes the state of the diff, and the brief asks the agent to finish or fix it rather than build from scratch.

Title: Finish the contributor's `--json` output flag for `triage list`

```markdown
Type: slice
Part of: none
Blocked by: none

## What to build
External PR #57 adds a `--json` flag that serialises the issue list to JSON.
The happy path works and the diff matches the project's command structure.
Two gaps remain: errors are still printed as human text, and the flag has no
test coverage. Finish the diff.

## Behaviour
- `triage list --json`, success → well-formed JSON on stdout.
- `triage list --json`, error → `{ "error": string }` on stdout.
- Exit codes match the non-JSON command.
- No flag → human-readable output, untouched.

## Approach constraints
Reuse the serialiser the PR already added; don't introduce a second.

## Verify
The command's test suite, plus a byte comparison of default output before
and after.

## Acceptance criteria
- [ ] `triage list --json` emits valid JSON for success and error cases (test)
- [ ] Exit codes match the non-JSON command (test)
- [ ] A test covers the `--json` success output and one error case (test)
- [ ] Default output is byte-for-byte unchanged (`cmp` against main's output)

## Out of scope
- Adding `--json` to any other command
- Changing the JSON shape of the success payload the PR already defined

> *This was generated by AI during triage.*
```

### Bad agent brief

```markdown
## Agent Brief

**Summary:** Fix the triage bug

**What to do:**
The triage thing is broken. Look at the main file and fix it.
The function around line 150 has the issue.

**Files to change:**
- src/triage/handler.ts (line 150)
- src/types.ts (line 42)
```

This is bad because:
- Not on a ticket template: no `Type:`, `Part of:` or `Blocked by:` lines
- Vague description ("the triage thing is broken")
- References file paths and line numbers that will go stale
- No acceptance criteria, let alone ones that name their proof
- No scope boundaries
- No description of current vs desired behaviour
