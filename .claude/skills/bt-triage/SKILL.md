# Triage

Move raw issues on the project issue tracker through a small state machine. A raw issue is one an agent didn't create: a report from the owner or from outside. A bug an agent found skips triage (`docs/agents/steps/bugs.md`).

If this repo treats external pull requests as a request surface (`docs/agents/issue-tracker.md`), triage covers them: **a PR is an issue with attached code**, same roles and states, with deltas in EDGE-CASES.md. Resolve a bare `#42` per the tracker config.

Every comment or issue posted during triage **must** end with this disclaimer:

```
> *This was generated by AI during triage.*
```

## Invocation

Invoked by the orchestrator during housekeeping, or by the owner in natural language. Act on requests like "show me anything that needs my attention", "look at #42", "move #42 to ready-for-agent", "what's ready for agents?"

## Show what needs attention

Query the tracker (`gh issue list`, `ticket.py status`); present three buckets, oldest first. Skip issues an agent created (agent signature in body or first comment).

1. **Unlabelled**: never triaged.
2. **`needs-triage`**: evaluation in progress, including reporter replies since the last triage notes.
3. **`needs-info` whose decision ticket the owner has answered**: needs re-evaluation.

Include external PRs when in scope, tagged `[PR]` or `[issue]` (EDGE-CASES.md). Show counts and a one-line summary per item, then work oldest first.

## Triage a specific issue or PR

Keep drafts and scratch output in `.work/tickets/<n>/`, where `<n>` is the raw issue's number.

1. **Gather context.** Read the issue or PR (body, comments, labels, author, dates; the diff for a PR). Parse prior triage notes; don't re-ask resolved questions. Explore the codebase with its domain glossary, respecting ADRs. Run two checks: (a) **redundancy** — search for an existing implementation by domain concept, not just the request's wording, and record where you looked; if found, it's an already-implemented `wontfix` (step 5); (b) **prior rejection** — read `.out-of-scope/*.md` and surface anything resembling this request.
2. **Recommend.** Decide category and state (ROLES.md) with reasoning and a short codebase summary, including whether it's already implemented. Routine calls are yours; a product call means filing a decision ticket (`docs/agents/steps/decisions.md`), then stopping.
3. **Verify the claim.** Before grilling, check it holds up. For a bug, reproduce from the reporter's steps; for a PR, run the relevant tests or commands on the diff. Record: confirmed (with code path), failed, or insufficient detail (EDGE-CASES.md). A confirmed verification makes a much stronger brief.
4. **Grill (if needed).** Use the `bt-grilling` skill, then `bt-domain-modeling`. Grill the owner a round at a time, sharpening domain terms and updating `GLOSSARY.md`/ADRs inline as decisions land.
5. **Apply the outcome** (filing, promoting and closing: `docs/agents/steps/bugs.md`, "Triage outcome"):
   - `ready-for-agent`: write the brief ([AGENT-BRIEF.md](AGENT-BRIEF.md)).
   - `ready-for-human`: the same, with a line saying why it can't be delegated (judgement, external access, design, manual testing).
   - `needs-info`: the decision ticket from step 2 holds the question; post the notes below on the raw issue so the work isn't lost.
   - `wontfix`, with the comment depending on *why*: already implemented (point to where it lives), rejected bug (why it isn't), or rejected enhancement (only after the owner decided, or a matching `.out-of-scope/` file; link it).
   - `needs-triage`: apply the role. Optional signed comment if there's partial progress.

## Needs-info template

```markdown
## Triage Notes

**What we've established so far:**

- point 1
- point 2

**What we still need from you (the reporter):**

- question 1
- question 2

> *This was generated by AI during triage.*
```

Capture what grilling resolved under "established so far". Questions must be specific and actionable. An owner's question lives in the decision ticket; the notes point to it.
